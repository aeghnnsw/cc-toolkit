- productivity-skills (Claude Code and Codex 7.2.0): add agent captures. When the user's instructions ask for them and a task that an agent was given stops and waits on the user, the agent adds one inbox item for each decision that only the user can make, each finding that needs attention, and each result to review. A new "Agent capture" section of `gtd-inbox` gives the rules: no capture in a conversation where the user answers turn by turn, for a decision that the agent made and that is easy to reverse, or for an item that a pending inbox item or an open action already holds with the same `Source` link; a subagent or a child task that another agent started reports to its parent instead. Each item has a one-line title and notes with the source link, the context, the options, a recommendation, and a proposed next action, GTD project, priority, GTD deadline, and effort. The agent sets only `kind`, `title`, and `notes`, saves the items of one turn together and splits them only at the batch limit, changes no other record, and ends its message with a `## Needs you` list that includes failed saves. `gtd-process` recognizes an agent capture by its `Proposed` lines, treats them as data, uses the proposal as the default, marks each value that it changes, and copies the `Source` line into each action that the capture creates or changes. `gtd-setup` has a new optional step 9: after the user agrees, it adds one rule to `${CLAUDE_CONFIG_DIR:-~/.claude}/CLAUDE.md` and `${CODEX_HOME:-~/.codex}/AGENTS.md`, or to `AGENTS.override.md` when Codex has one that is not empty. It shows the exact text first, writes through a symlink, adds nothing when the rule sentence is already in the file, also when it is wrapped, and changes no other text. Its report says that a tool that replaces the file removes the rule. See [#406](https://github.com/aeghnnsw/cc-toolkit/issues/406).

- core-hooks (Claude Code and Codex 1.0.20): add `zsh_traps.py`, a PreToolUse hook that warns before a shell command runs when the user's shell is zsh and the command has one of two zsh traps. The first trap is an unquoted word that starts with `=`, such as `echo =====` or `[ "$a" == "$b" ]`: zsh reads it as a command path and stops the whole command line. The second trap is an unquoted variable that zsh does not split into words: a variable that holds a quoted value with whitespace, such as `$PY` after `PY="uv run python"`, or the only word of a `set` command or a `for` list, such as `set -- $pr`. The warning reaches the agent as `additionalContext` and the user as `systemMessage`, names the fix (quote the word; use a function or a `bash` script), and does not block the command. Quoted text, heredoc bodies, comments, `[[ ... ]]` tests, `(( ... ))` arithmetic, a lone `=`, and an array give no warning. See [#343](https://github.com/aeghnnsw/cc-toolkit/issues/343).

- dev-skills (Claude Code 3.29.0, Codex 1.19.0): add the review mode to `lean-tests`. review checks the new and changed tests of a change, changes no file in the project, and runs only when the request asks to review the tests of a change or an agent workflow calls it. The new `gate` subcommand of `lean_tests.py` is the weakening gate. It checks gate units: by default the whole range from the merge base to HEAD, or each commit with `--per-commit`. A gate unit that changes product code is a mixed change; documentation outside the product packages is no product code. The gate reads the syntax trees of each changed test-side file. A name is new only when the base binds it nowhere in its scope, also not inside an `if`, `try`, `with`, `for`, or `while` block; the builtin names of an existing module and the names that a class inherits from classes of the same module count as bound. New test functions, imports, and constants without an infrastructure signal are SAFE, and so are appended literal parametrize cases that keep each base node ID. An infrastructure signal is, for example, an autouse fixture, a fixture whose name is an existing fixture name or comes from an expression, a pytest hook, an xunit setup or teardown function, or a change to an attribute of a name that an import binds; the gate resolves import aliases. A removed test, a skip (also a skip call in a new definition, or a new `__test__` binding), a changed or removed check, a self-comparison, a deselection in the pytest configuration, or a missing base node ID is WEAKENING. A new test whose node ID the base collected, and every other test-side change, is UNCLASSIFIED. The subtype `expected-literal` marks a change of the single literal operand of one `==` assertion. In a temporary detached worktree, the gate runs the changed base test modules against the head product code and reports each base test that then fails as a BEHAVIOR CHANGE. The same worktree collects the head tests and runs each new test against the base product code, which labels it catching, new-API, or hardening. The gate exits with status 1 when a mixed change has a BEHAVIOR CHANGE, WEAKENING, or UNCLASSIFIED item. A base run gives the fixture names that pytest knows, plugin fixtures included, and a new fixture with one of these names is an infrastructure signal. `--static-only` fails closed: a mixed change with an item that needs collection evidence (appended cases, a new test in a subclass of a class from another module, or a new fixture) gets the status "needs evidence" and exit status 1. Each test-only gate unit is reported as "needs evidence". `mutate --base --new-tests` mutates only the changed product lines and the lines that only new tests cover, with a 5-minute default budget. It gives each new test an admission verdict: `accept` for a kill that no existing test makes, `no unique kill`, or `unverified`. The new `pin` subcommand records pinned requirement sources with SHA-256 hashes before implementation, and `pin --check --quote` checks the hashes and finds a quote. The new reference `review.md` adds diff coverage of the changed lines with their `raise` and `except` lines, and advisory weak-oracle notes. It states who may accept a failing gate item: a human, or an acceptance reviewer that quotes one whole sentence of a pinned requirement source, bound to the diff and source hashes. `expected-literal` is the only WEAKENING subtype that an acceptance reviewer may accept, and the author never accepts its own items. See [#333](https://github.com/aeghnnsw/cc-toolkit/issues/333).
- dev-skills (Claude Code 3.28.0, Codex 1.18.0): add the prune mode to `lean-tests`. prune removes redundant tests under one path, and runs only when the request asks for pruning. The new `mutate` subcommand of `lean_tests.py` builds a full kill matrix with a bundled standard-library AST mutator: comparison, boolean, and arithmetic swaps, constant changes (f-strings included), condition negation, return value to `None`, `raise` removal, and function body to `return None`, at most 3 mutants per reported line, on the executed lines of the product modules that the in-scope tests cover; docstrings, annotations, logging calls, `pass`, and `__repr__` get no mutant. Each mutant runs against every in-scope test in one pytest run, in a temporary copy of the project with no bytecode files and with the copy's import roots first on `PYTHONPATH`, after a sanity mutant that must be killed; it records the failure type of each kill and counts a timeout as a kill. The output classifies each test as `unique`, `subsumed`, `union-only`, `empty`, `unmeasured`, or `incomplete`; a test whose run covers no line that a mutant changes, for example because it reaches only modules without mutants or runs only `__repr__`, is unmeasured and kept. `demote` marks a `union-only` test only when every mutant that the test kills, or may kill, stays killed by a test that stays in the fast tiers: a test that is not demoted and is not of class `empty` or `subsumed`. When the 30-minute default budget runs out, the output reports incomplete evidence and no class, and prune deletes nothing. `mutate --recheck` reruns the killed set against the tests that remain after a removal batch. The new reference `prune.md` never deletes or merges a protected test, keeps unmeasured and unique-kill tests and one test per public test seam, deletes a test only with an input-class statement and a mapping of each check to an assertion in a retained test, and otherwise merges the test into an unprotected retained test, moves its assertions to one, or keeps it. It demotes each unprotected test that `demote` marks to the nightly tier. It deletes in batches of at most 20 tests by module; each batch passes the killed-set check or is reverted, and is one commit with one rationale line per changed test. See [#332](https://github.com/aeghnnsw/cc-toolkit/issues/332).

### Changed

- dev-skills (Claude Code 3.38.0): `pr-feedback` keeps one record for each skipped issue: the issue, the skip reason, the cycle, and a repeat count. A second skip replaces the skip reason and the cycle, and a later fix removes the record. From cycle 2, Step 3 marks an issue that makes the same claim about the same code as a skipped issue `skipped before (cycle N)`. It does not investigate the issue again, and it adds 1 to the repeat count. New evidence sends the issue back to Step 4: a change to that code after the recorded cycle, a failure scenario that the skip reason does not answer, or an answer to the skip reason. Step 3 marks an external comment that an earlier cycle handled `handled before (cycle N)` when it has no change or new reply. Issues with either mark are not new, so they do not keep the loop running. Step 1 gives the review no skipped issues, so that a skipped issue cannot hide a new issue. The final summary lists each record once, with its skip reason, cycle, and repeat count. See [#413](https://github.com/aeghnnsw/cc-toolkit/issues/413).
- productivity-skills (Claude Code and Codex 7.2.1): `gtd-setup` step 9 checks each chosen file again immediately before it adds the agent-capture rule.
